## 過去Windows基準との微差の切り分け（2026-10-17 JST）

付属の `vendor/tests/p2p/test01.out`（VOACAP 16.1207W、Windows）と、同じ入力を現行エンジン（voacapl 0.7.7、gfortran 13.3、x86-64 Linux）で実行した出力を、全行・全セルで比較した。

- 比較した数値は24時間×全行の5848セル。異なったのは135セルで、すべて最後に印字した桁の1単位だけ（V HITEの1セルのみ2 km）。CHUCKが使う項目では、REL 3、S DBW 3、SNR 1、TANGLE 3、MUF 1セル。
- エンジンの印字直前の値を出力する計測版を作業用にビルドし、差のある整数・小数2桁の24セルについて丸める前の値を調べた。全セルが丸めの境界から0.03単位以内にあった（例：REL 0.984924がWindowsで0.99、現行で0.98。S DBW −43.500023がWindowsで−43、現行で−44）。境界から離れたセルに差はない。
- gfortranの最適化を変えても（`-O0`、`-O2`、`-mfpmath=387`、`-ffp-contract=off -ffloat-store`）出力は `-O2` と同一または1セル差で、Windows基準との差はほぼ変わらない（134〜135セル）。このため、差の原因はビルド設定ではない。
- 2026-10-17のMacでの比較でも、arm64とamd64のLinuxイメージの間で、CHUCKが使わないRPWRG・SNRxx・V HITEだけが末位で±1異なった。
- 結論：計算式・係数の違いではなく、コンパイラーと数学ライブラリの違いで生じる1e−4程度の計算差が、丸めの境界付近の値だけ印字の末位を変えている。

これに基づき、`scripts/compare_voacap.py` はWindows基準との差を参考記録から判定に変えた。許容差は印字の末位1単位（REL 1ポイント、SNR 1 dB·Hz、受信信号1 dB、打上げ角0.1°、MUF 0.1 MHz）とし、超えた場合は終了コード1にする。CHUCK API と同梱エンジン直接実行の差は従来どおり0を要求する。
